## 1. Project overview

Bhav Bhakti is a devotional content app: wallpapers, ringtones, daily horoscopes (Rashifal), quizzes, and a social "feed" of devotional content (mantras, etc.).

Two sibling repos live under this parent folder (`D:\bhav_bhakti`, which is **not itself a git repo** — only the two subfolders below are):
- `bhav-bhakti-fe` — Expo / React Native frontend (Expo Router, TypeScript, Zustand, `expo-av`). GitHub: `orivori/bhav-bhakti-fe`.
- `bhav-bhakti-be` — Express / Sequelize backend (MySQL). GitHub: `orivori/bhav-bhakti-be`.

**Founder context:** solo, non-technical founder. No dev team — all implementation work goes through Claude Code. When a decision has technical tradeoffs, explain them in plain language before the founder has to choose.

## 3. Content ingestion — known gap

**There is no admin panel, dashboard, or CMS anywhere in either repo.** Confirmed by direct file search — nothing named admin/CMS/dashboard exists in the frontend at all.

Current real-world workflow for adding content is one of:
1. Manual API calls (Postman/curl): `POST /api/v1/upload/media` to get a Firebase URL back, then `POST /api/v1/feed` with that URL in a `media[]` array to create the `Feed`/`FeedMedia` rows.
2. `npm run import:feeds` (`scripts/import-feeds-from-csv.js`) — reads a CSV (exported from a Google Sheet) and inserts `Feed`/`FeedMedia` rows directly via Sequelize, bypassing the API. The CSV itself still instructs the human filling it out to "upload on s3, take url from cloudflare and put here" — i.e. the sheet-based process predates the Firebase migration and hasn't been updated.

**Security note, not urgent right now:** `POST /api/v1/feed` (`src/routes/feed.routes.js:16-23`) has its auth check commented out — `// authenticate, // Commented out for public access` — with a comment saying it was made public "for admin web interface." That web interface was never built, so right now this content-creation endpoint is open to anyone who finds it. Flag as a pre-launch fix, not something to silently patch without asking (removing it will break the current manual-curl workflow until a real admin auth story exists).

**Priority:** a simple, non-technical-friendly content upload tool is a near-term goal. Don't assume this has been built in a future session without checking — confirm with the founder first.

**Content management decision — three options being weighed, not yet decided (2026-07-19), pending a discussion with the co-founder.** This supersedes the single "agreed plan" from 2026-07-18, which is now folded in as option (b):
- **(a) Adapt the existing CSV importer for Firebase URLs** — cheapest, ~1-2 hours. `scripts/import-feeds-from-csv.js` already reads `title_hi`/`caption_hi` columns correctly (see §9) and just needs its expected URL format updated for Firebase instead of the old S3/CloudFront convention. Matches the co-founder's established bulk-upload habit from the AWS era. Downside: no editing or deleting after import — mistakes require a direct DB fix.
- **(b) Build a minimal custom admin upload tool** — ~3-5 hours. The original 2026-07-18 plan: a single-page local-only form (file picker, type dropdown, category dropdown populated from `GET /categories?type=`, a title field) that calls the existing `POST /upload/media` then `POST /feed` endpoints in sequence — no new backend functionality needed. Form-based, one item at a time, but includes basic edit/delete unlike (a). The one backend change this needs: gate `/upload/media` and `/feed` behind a simple shared-secret middleware (header/query param checked against an `ADMIN_KEY` env var) — **not** real user auth, since `authenticate` runs through the broken OTPless flow (see §2) and would buy nothing.
- **(c) Adopt Directus as a full CMS** — ~1-2 days. Confirmed compatible with the existing MySQL schema via a full audit: real FK constraints already exist (`Feed→Category`, `Feed→Deity`, `FeedMedia→Feed`, quiz nesting), so Directus can sit on top with no restructuring needed. Offers native bulk CSV import *and* editing/deletion *and* multi-user roles — the most capable option. Costs the most setup time (multilingual JSON fields need per-column interface configuration; role/permission setup to hide PII/analytics tables takes real effort), and requires an ongoing schema-change discipline: structural changes only ever happen via Sequelize migrations in `bhav-bhakti-be`, never through Directus's own Data Model UI, or the ORM and the live DB schema will drift apart.
- **Wallpapers tab fix is blocked regardless of which option is picked** — see §10. Fixing its data source is pointless until a reachability decision is also made (new tab slot vs. a link from Home), so don't treat shipping any of (a)/(b)/(c) as automatically unblocking that fix.

## 15. 2026-07-23 session — Animation fix, autoPlay-on-tap fix, Ringtones migrated to expo-audio (verified on device), USB dev-build crash fix, two non-bugs confirmed

**Wave/pulse/rotate animation freeze — DONE, COMMITTED (`1e4d09c`).** `audio-player.tsx`'s wave visualizer, play-button pulse, and loading spinner all silently stopped animating after about a second, even though playback and `isPlaying` state kept working correctly. Root cause: `pulseAnim`, `rotateAnim`, and `waveAnims` were declared as plain `const`s (`new Animated.Value(...)`) directly in the component body instead of `useRef` — every re-render created fresh, undriven instances, and the JSX always bound to whichever instance existed in the *current* render. Position-tracking re-renders fire every ~500ms during playback (expo-av's default status-update interval), so within about a second the visible bars/pulse were silently swapped onto new static values while the original animation loop kept running, invisibly, on the now-orphaned instances. Fixed by moving all three to `useRef(...).current` so the same instances persist across re-renders. Confirmed via investigation, not assumed: `pulseAnim` had the exact same bug but was easy to miss (single small icon, subtle 1.0→1.1 scale, vs. 20 obviously-frozen bars); `rotateAnim`'s loading-spinner window is normally too short-lived to ever hit a position-tracking re-render before `isAudioLoading` flips back to `false` on its own, so it likely never visibly manifested in practice even though the code had the identical flaw.

## 17. 2026-07-23 session (continued) — global playback coordinator built, tested on-device, and shipped

**Global playback coordinator — DONE, COMMITTED (`3de37e5`), THOROUGHLY TESTED ON-DEVICE (7/7 scenarios — see below).** Built `src/store/playbackStore.ts` (Zustand, deliberately **not** wrapped in `persist` — unlike every other store in `src/store/`, since it holds live imperative closures (`stop`/`pause`/`seekTo`) bound to a specific mounted player instance; persisting and rehydrating those across an app restart would leave them pointing at a player that no longer exists). The store holds **two independent slots**, not one shared "now playing": `ephemeral` (ringtones) and `persistent` (mantra today, aarti/bhajan/stories later). Hand-off rules are asymmetric by design:

- **Cross-mode hand-off**: a ringtone preempting persistent content **pauses** it (kept in the store, `isPlaying: false`, still resumable) rather than clearing it; persistent content preempting a ringtone **fully stops** it (ringtones have no paused/resumable UI to preserve, so there's nothing to keep).

**Real race condition found and fixed (verified via an isolated test with controllable timing, not just reasoned through): reopening the SAME content shortly after cancelling its background download could collide with that cancellation's own cleanup**, producing on-device symptoms of `Download failed with status 400` / `Network request failed`, self-resolving after waiting. Root cause: `cancelBackgroundDownload` removed the feedId from its tracking Map *before* the actual native cancellation (`cancelAsync()`) and partial-file delete had finished — a fresh download attempt for the same feedId landing in that gap could start a second `DownloadResumable` targeting the exact same destination file while the first was still tearing down. **Fixed in `audio-player.tsx` only** (not yet backported to `RingtoneFeedCard.tsx` — see below) via a per-feedId `inFlightCancellations: Map<string, Promise<void>>` that both `getCachedLocalUri` and `downloadToCacheInBackground` check before touching the same feedId's cache file again, plus a `queuedForBackgroundDownload` dedup guard closing a secondary nested race (multiple rapid re-attempts during the same wait window previously could have each scheduled their own duplicate deferred start). **Confirmed zero added delay in the common case** via the isolated test: when nothing is pending (the overwhelming majority of calls), the `await` is skipped entirely via an `if (pendingCancellation)` guard, not just fast — the test measured a real download registering synchronously (~2ms, console.log overhead only) with no cancellation involved.

Worth backporting in a future pass, same class as the already-logged feedId-vs-title cache-keying and failed-download-cleanup asymmetries between these two files (§24).

**Separate crash found and fixed in the same pass: `clearLockScreenControls` could throw "Cannot use shared object that was already released" during rapid feedId switching.** Two call sites were unprotected — the playback-coordinator's `stop`/`pause` closures (called externally by the MiniPlayer) and the screen's unmount-cleanup effect — both now wrapped in try/catch. **Deliberately not AppState-gated**, unlike the earlier `setActiveForLockScreen` crash fix (§18): that gating exists specifically because *starting* a foreground service is what Android 12+ restricts during background/foreground transitions, which doesn't apply to *clearing* one — this crash is a native shared-object lifecycle issue (the object was already released), which try/catch is the correct guard for, not AppState timing.

**MAJOR ARCHITECTURAL FINDING, root cause identified via direct native source inspection — fixed the next day, see §26.** Opening any fresh, never-before-played content while a *different* item sits paused in the mini-player can show a false "network request failed"-style error (`audioConnectionError`'s exact text: "Audio Not Available" / "check your internet connection") that self-resolves shortly after being dismissed. **Confirmed as a genuinely separate bug from the race just fixed above** — not a JS-level same-feedId collision, but native-layer HTTP connection-pool exhaustion between two *different* feedIds. Root cause, traced directly in the bundled native Android source (both `expo-audio` and `expo-file-system` ship their native Kotlin source inside `node_modules`, not just compiled artifacts):
- `expo-audio`'s `AudioModule.kt` (`android/src/main/java/expo/modules/audio/AudioModule.kt:50`) creates a single `OkHttpClient()` with no custom `Dispatcher`, wired into every `AudioPlayer` instance app-wide via `OkHttpDataSource.Factory(httpClient)` — meaning it inherits OkHttp's hardcoded default `maxRequestsPerHost = 5`, shared across every mantra/ringtone/aarti/bhajan player in the whole app, not scoped per-screen or per-player.
- `expo-file-system`'s own separate `OkHttpClient` (`FileSystemLegacyModule.kt:1000-1011`, used by the background cache downloader above) has the identical unconfigured-default characteristic, independently.
- When content A is paused, ExoPlayer commonly keeps its stream connection warm (buffered/read-ahead) rather than closing it immediately, for instant resume. Tearing that connection down via `Call.cancel()` is not instantaneous, and measurably slower for larger, more-buffered files (matches the on-device observation that this is worse with larger files, barely noticeable with smaller ones). While that teardown is still in flight, it can still be occupying one of the 5 per-host slots in the *same shared* `httpClient` that a fresh item B's `player.replace()` needs a slot from.
- **Confirmed precisely, not just inferred, that B's own 10-second client-side load-timeout is what's actually firing** (`audio-player.tsx`'s `isAudioLoading`/`nativeLoadStarted` effect) — the exact displayed Alert text only ever comes from that one `setTimeout`, and it has no Retry button (matches what was observed) unlike the *other*, differently-worded playback-error alert in `togglePlayback`'s own catch block. Dismissing it only clears the JS-side loading flag; it does not cancel B's underlying native load, which keeps trying in the background regardless and typically succeeds once the connection-pool contention clears on its own — exactly matching the observed "becomes playable after dismissing the error" behavior, with no actual permanent network failure ever having occurred.

**Important reframing, worth remembering:** this connection-pool bug is **not** a consequence of this session's caching work — it would occur even with zero caching/download-related code, purely from the mini-player's intentional "keep paused content alive so it's instantly resumable" design combined with `expo-audio`'s shared, unconfigured native HTTP client. It's a pre-existing architectural characteristic of the persistent player (present since the global playback coordinator was built, §17), only now surfaced because this session was the first time real, varied, larger-file content existed to actually test "pause one thing, immediately play something completely different."

**Proposed fix directions for the connection-pool bug, weighed the next day (§26):**
(a) Don't rely on `player.pause()` alone to free A's connection — explicitly detach/release A's media source before B loads.
(b) Configure a less conservative per-host connection limit on `expo-audio`'s `httpClient`, if that's exposed/patchable without forking the native module. **This is the option that was chosen and built — see §26.**
(c) Extend B's own client-side timeout/retry tolerance to absorb the contention window rather than eliminating the contention itself.

**Also flagged, not yet decided, worth revisiting:** whether the full caching/cancellation complexity built across this session is proportionate given the app currently has zero real users, versus reverting to simple direct streaming (no local caching at all) and deferring caching until real usage/bandwidth-cost data justifies it. Genuinely open, not leaning either direction yet — still an open question as of §26, not resolved by the connection-pool fix.
